Okay, so HackerNews had some fascinating security discussions today that really highlight how fragile even old, well-tested software can be. There's this thing called "sshhole," which is a vulnerability in OpenSSH, and the discussion around it is genuinely instructive about how software security actually works.

So here's the core issue. SSH is how you log into remote systems, and it validates your password by running it through a cryptographic function and checking if it matches the stored hash. But this relies on this assumption that the stored hash is always legitimate—it should never be like a special marker value that means "error" or "no password." Except sometimes it was. And that created this gap where an attacker could potentially make the authentication function return an asterisk, which would match a specifically corrupted hash, and boom—unauthorized access.

The discussion gets really interesting because it's not just about this specific bug. It's about what the security community calls "in-band signaling"—the idea that you're using the same channel for both data and out-of-band information. Like, using an asterisk or an exclamation point to mean "this account doesn't have a password" instead of using a proper error code or return value. It's clever in a way, and it worked for decades, but it's also brittle. One person points out that Musl, which is an alternative C library, had already worked around this kind of failure in one place but then forgot to do it in another place, which created its own vulnerability.

What's fascinating is the broader debate this surfaces about why old, long-established software isn't necessarily more secure just because it's been around forever. One commenter makes this really sharp point: "There's been a lot of time for cruft to accumulate until no-one can ever fix it because everyone is expecting it to function in the broken manner it's always functioned." In other words, you get stuck with legacy behavior because changing it breaks things that depend on it, even when that legacy behavior is actively dangerous. It's this tragedy where software archaeology and operational reality collide.

And then there's a fair amount of criticism of the Musl developers for making convenience-focused changes to core crypto functions without, apparently, the level of auditing that would've caught this stuff. It's a good reminder that convenience and security are often in tension, and when you're working on cryptographic fundamentals, convenience usually has to lose.
